ARB Review Pre-Preparation Guide

v0.2·Last updated: 2026-08-10
This document describes the pre-authorization setup procedure required for the ARB (Architecture Review Board) team to perform an infrastructure review of your service.
The process is complete once you deploy 2 CloudFormation stacks.
Thank you for your cooperation.

1. Overview

This process creates read-only resources including an IAM Role so that the ARB team can review the resource status of your service's AWS account.

ItemDetails
Permission ScopeAWS managed policy ReadOnlyAccess (no write/delete permissions)
Authorized PrincipalOnly a specific Role from the ARB team account (260544022684) can Assume this role
Deployment MethodUpload stacks via the CloudFormation web console (AWS CLI not required)
Estimated TimeApproximately 10 minutes (add 3–5 minutes per additional region for regional stacks)
After ReviewDeleting the created stacks will also remove all associated resources and permissions

Overall Flow

👥  Service Team
  1. STEP 1. Deploy Global Stack (us-east-1, once) → Creates IAM Role
  2. STEP 2. Deploy Regional Stack (for each region with target resources) → Configures per-region resource access
  3. STEP 3. Share Role ARN with the ARB Team

🔍  ARB Team
Performs ARB Review
▼
👥  Service Team
STEP 4. Delete stacks after receiving review completion notification

2. Prerequisites

  • 2 CloudFormation template files (download using the buttons below)
  • Administrator-level (or equivalent) console access to the service AWS account
  • List of regions used by your service

3. STEP 1. Deploy Global Stack Once in us-east-1

1

Open CloudFormation in the AWS Console

  1. Log in to the service AWS account.
  2. Change the Region selector in the top-right corner to US East (N. Virginia) · us-east-1.
    💡 Deployment Region Note IAM is a global resource, so it works the same regardless of which region you deploy from.
    However, this guide uses us-east-1 as the standard region for management convenience.
    You may deploy from any other region you are comfortable with.
  3. Type CloudFormation in the service search bar and navigate to it.
2

Create Stack

  1. In the left menu, click Stacks → then Create stack (top-right) → With new resources (standard).
  2. Prepare template: Select Choose an existing template.
  3. Template source: Select Upload a template file and upload 01-global.yaml.
  4. Click Next.
3

Enter Stack Name

  1. Stack name: arb-readonly-global (recommended)
  2. There are no parameter input fields. Click Next.
4

Stack Options and Review

  1. On the Configure stack options page, leave most settings at their defaults. At the bottom, in the Capabilities section, check the checkbox: 
    ☑ I acknowledge that AWS CloudFormation might create IAM resources with custom names.
    This template creates an IAM Role with the fixed name ARB-ReadOnly-Role, which requires checking the above item.
    You cannot proceed to the next step without checking it.
  2. Click Next.
  3. On the Review page, verify the inputs and click Submit.
5

Confirm Deployment Completion

  • When the Status shows CREATE_COMPLETE, the deployment is successful (takes 1–2 minutes).
  • If you see CREATE_FAILED, refer to the FAQ.

4. STEP 2. Deploy Regional Stack Repeat for each region with target resources

Deploy this stack in every region that contains at least one of the target resources listed below.
If your service uses multiple regions, repeat this step for each region.

💡 Prepare the Role ARN Before Starting

This stack requires the ARN of the IAM Role created in STEP 1 as a parameter.
If you haven't noted it yet, go to the arb-readonly-global stack in us-east-1 CloudFormation → Outputs tab → copy the RoleArn value.

(You will use the same value in STEP 3 as well)

Target Resources

The regional stack configures ARB read access for the following resource types.

Resource TypeCorresponding ParameterDescription
EKS Cluster EksClusterName1 ~ EksClusterName5 Creates an Access Entry (ViewOnly) per cluster

Fill in only the parameters that correspond to resources you use; leave the rest blank.
If there are no target resources in a given region, you do not need to deploy this stack there.
(You may deploy with empty values for future extensibility if you prefer.)

1

Navigate to the Target Region

  1. Change the region selector in the top-right corner to the region you want to deploy in. e.g., Asia Pacific (Seoul) · ap-northeast-2
  2. Navigate to the CloudFormation service.
2

Create Stack and Upload Template

  1. Create stack → With new resources (standard).
  2. Select Upload a template file, upload 02-regional.yaml, and click Next.
3

Enter Parameters

  1. Stack name: arb-readonly-regional (recommended)
  2. Fill in the Required section:
    ParameterValue
    ARB Role ARN Copy and paste the RoleArn value from the Outputs tab of the arb-readonly-global stack created in STEP 1
    arn:aws:iam::<Account ID>:role/ARB-ReadOnly-Role
  3. Fill in the EKS Clusters in this region (optional, up to 5) section:
    • Enter the EKS cluster names in this region starting from EKS cluster name #1.
    • Fill in only as many fields as you have clusters; leave the rest blank.
    💡 How to Find EKS Cluster Names Check in the console under Elastic Kubernetes Service → Clusters, or
    use the CLI command aws eks list-clusters --region <region>.
  4. Click Next.
4

Stack Options and Review

  1. On the Configure stack options page, leave defaults and click Next.
    This stack does not create IAM Roles, so the Capabilities checkbox will not appear.
  2. On the Review page, verify the inputs and click Submit.
5

Repeat for Other Regions

Repeat steps 1–4 above for each region that has target resources.

✅ STEP 2 Completion Criteria STEP 2 is complete when the arb-readonly-regional stack shows CREATE_COMPLETE status in all regions with target resources.

5. STEP 3. Share Role ARN with the ARB Team

Once all stacks are deployed, share the Role ARN with the ARB team.

1

Copy the Role ARN

  1. Change the region to us-east-1.
  2. Go to CloudFormation → click the arb-readonly-global stack.
  3. Navigate to the Outputs tab.
  4. Copy the Value from the row where Key is RoleArn. 
    arn:aws:iam::<Service Account ID>:role/ARB-ReadOnly-Role
2

Send to the ARB Team

✅ What to Share Send the Role ARN copied above to the ARB team contact.

Once shared, the pre-preparation phase is complete.
Wait for the ARB team to perform the review, and proceed to STEP 4 after receiving the review completion notification.

6. STEP 4. Cleanup After Review Completion

After receiving the review completion notification from the ARB team, delete the created stacks.
The deletion order is important.

⚠️ Deletion Order

You must delete all regional stacks first, then delete the global stack.

If you do not follow this order, the IAM Role may be deleted first, leaving the Principal ARN referenced by regional resources in an orphaned state.

1

Delete Regional Stacks (in all deployed regions)

  1. Navigate to the CloudFormation console in each region.
  2. Select the arb-readonly-regional stack and click Delete.
  3. Once the Status shows DELETE_COMPLETE, move to the next region.
2

Delete Global Stack (us-east-1)

  1. Change the region to us-east-1.
  2. Select the arb-readonly-global stack and click Delete.
  3. Once the Status shows DELETE_COMPLETE, the cleanup is finished.
3

(If Applicable) Delete Auto-Generated S3 Buckets

  1. In the S3 console of each region where you deployed STEP 1 and STEP 2, look for buckets starting with cf-templates-.
  2. Check the creation date of the bucket to confirm it matches the time when you deployed STEP 1 / STEP 2.
  3. If the creation date matches your deployment time, AWS auto-created this bucket during template upload, so it is safe to delete. Empty the bucket first, then Delete it.
  4. If the creation date is earlier than your deployment, the bucket existed before, so leave it as is.

For more details, see FAQ.

✅ Cleanup Complete Once all stacks are deleted, the ARB team can no longer access your service account.

7. FAQ / Troubleshooting

Q1. Can I change the Role name?

No. The ARB team's automation tools operate based on the name ARB-ReadOnly-Role.
The RoleArn parameter in the regional stack also requires this name to pass validation.

Q2. I'm getting CREATE_FAILED in STEP 1.

It is likely that a Role with the same name (ARB-ReadOnly-Role) already exists in the account. Check for duplicate Roles in the IAM console. If it serves the same purpose, find and reuse the existing stack, or delete the conflicting Role and retry.
If you lack permissions to create Roles, please contact your account administrator.

Q3. I entered the wrong EKS cluster name in STEP 2.

If you enter a non-existent cluster name, the Access Entry creation will fail.
Delete the stack and redeploy with the correct name, or use Update stack to modify the parameters.

Q4. I need to deploy in an additional region. Do I have to start over?

No.
Simply deploy 02-regional.yaml in the new region's CloudFormation console.
The global stack remains unchanged.

Q5. I created additional resources during the review. Do I need to redeploy?

The IAM Role uses the ReadOnlyAccess managed policy, so newly created resources are automatically queryable.
However, if a new EKS cluster was created, use Update stack on the regional stack in that region to add the cluster name.

Q6. Doesn't this Role have overly broad permissions?

ReadOnlyAccess is an AWS-managed policy that only includes view permissions (Get/List/Describe) for all services.
Write/modify/delete operations are not possible.
Additionally, the Trust Policy restricts Assume access to only a specific Role from the ARB account, blocking external access.

Q7. What is the cf-templates-* bucket?

When you upload a CloudFormation template file using Upload a template file for the first time,
AWS automatically creates a cf-templates-* bucket in that region and stores the template file there.
(If a cf-templates-* bucket already exists in that region, the existing bucket is reused.)

This bucket is not part of the stack resources—it is managed separately by CloudFormation itself, so it is not deleted when you delete the stack.
Since this is an auto-created bucket, your organization's S3 security policies may not be applied to it, which could cause it to be flagged during security audits.
If it was created specifically for this deployment, we recommend deleting it after cleanup.
